This is a read-only audit of the committed simulator and the completed August 14 publication bundle. The publication matrix is exactly 4 algorithms x 3 loads x 5 policies x 50 traces for each of the causal and zero-compute arms; the builder rejects any other coverage (`scripts/agx_build_final_publication.py:940-953`). ## 1. Executive architecture summary

The simulator is a discrete-event, continuous-time mission model. A trial creates a shared world, message bus, A* planner, and four independent robot shells, then attaches a global admission/reallocation scheduler (`known_visit_sim/core/scheduler.py:296-363`). Initial robot wakes are independently spread over the first 0.16 simulated seconds (`known_visit_sim/core/scheduler.py:365-371`; `known_visit_sim/config.py:45-50`). Absolute task-release events, bounded-wait timeouts, movement completions, allocator completions, message deliveries, and robot control wakes share one event clock (`known_visit_sim/core/scheduler.py:479-525`; `known_visit_sim/core/scheduler.py:847-868`).

At a control boundary, a robot either requests an allocation, services a task under its current cell, continues a queued turn/intent/move action, or replans (`known_visit_sim/core/robot.py:754-771`). Route planning is four-neighbor A* with movement, turn, searched-cell, and target-reward costs (`known_visit_sim/core/planner.py:9-18`; `known_visit_sim/core/planner.py:48-73`). A move is not instantaneous: it is scheduled to complete after a hash-keyed 1.5--1.7 s duration, so paired policies retain the same duration for the same robot/action/edge despite different event interleavings (`known_visit_sim/core/scheduler.py:42-81`; `known_visit_sim/core/scheduler.py:548-575`). Turn, collision-intent settlement, replan, and no-goal delays are 0.30, 0.10, 0.30, and 0.50 simulated seconds (`known_visit_sim/config.py:45-59`; `known_visit_sim/core/scheduler.py:1202-1218`).

The task-release process is exogenous. Eight of 50 tasks exist at time zero; the other 42 use accumulated exponential interarrival draws scaled by the selected rate, rounded to 9 decimal places (`study/manifests.py:155-182`). Release changes a task from UNRELEASED to RELEASED to PENDING at its predetermined absolute timestamp; admission is a separate scheduler action (`known_visit_sim/core/world.py:85-140`). Thus a low-load mission has a large exogenous lower bound from its final release, unlike a static known-target search.

The scheduler is allocator-independent. It queues released tasks and admits either immediately (Eager), when queue depth reaches B (Count and bounded), at the oldest task's release time plus W (bounded), on the final partial tail, or by piggybacking all pending tasks on a mandatory task-completion/invalid-goal/robot-idle epoch (`known_visit_sim/core/reallocation.py:521-586`). Admission clears the whole queue, exposes the admitted set to every robot, invokes each allocator's allocation-epoch reset hook, and queues one first-round context per robot (`known_visit_sim/core/reallocation.py:662-686`; `known_visit_sim/core/robot.py:185-232`).

One allocator call is one robot's `allocator.choose_goal` invocation, not a global auction and not an entire consensus convergence (`known_visit_sim/core/robot.py:569-648`). The simulator freezes every same-time robot input before executing any authoritative host decision. It then times the already-computed decision with a selected provider and commits each output only at `common virtual start + that call's duration` (`known_visit_sim/core/scheduler.py:593-725`; `known_visit_sim/core/scheduler.py:726-817`). Allocator messages and admissions arriving while that robot computes are buffered FIFO and applied after its result commits (`known_visit_sim/core/robot.py:172-183`; `known_visit_sim/core/robot.py:693-750`). Other robots and the event clock continue **in the virtual model**; the physical Python worker's synchronous wait is distinguished in Section 3.

For hardware trials, one long-lived worker owns one serial endpoint and one RP2040 board. The board keeps four persistent logical allocator contexts, one for each simulated robot; physical requests are necessarily measured serially, but their virtual completion times retain independent-processor semantics (`Simulation/Architecture/allocator_replay/causal/session.py:263-271`; `study/causal/worker.py:103-115`). The RP2040 recomputes the frozen allocator operation, and its goal, candidate count, messages, post-state, and mechanism class must match the authoritative host result before the measured duration is accepted (`Simulation/Architecture/allocator_replay/causal/session.py:466-490`; `Simulation/Architecture/allocator_replay/causal/session.py:741-776`).

The exporter reads each completed or retained algorithmic-outcome directory, records source/provider identities and file hashes, and selects a fixed set of trial metrics (`scripts/agx_build_final_publication.py:151-202`). It then builds exact causal/zero pairs, policy/Eager pairs, condition summaries, factor summaries, task-level descriptive summaries, hardware summaries, and noncompletion audits (`scripts/agx_build_final_publication.py:317-428`; `scripts/agx_build_final_publication.py:955-994`).

## 2. Exact metric definitions and formulas

Unless noted, all `*_s` fields are seconds and all counts are dimensionless. Trial-wide scheduler lists/counters start empty when the scheduler is constructed and stop when the trial returns after normal completion or an algorithmic/event horizon (`known_visit_sim/core/reallocation.py:458-471`; `known_visit_sim/core/scheduler.py:995-1018`). Allocator-work accumulation includes only calls with `valid_for_mission=True` and `parity_passed=True` (`known_visit_sim/core/reallocation.py:741-745`). “Event time” means the simulator's `state.clock_s`; “wall time” means a host or device monotonic timer.

### Why processor work can exceed mission elapsed time

Processor work is a sum across **calls and logical robots**. Same-start calls on different robots overlap in simulated time, yet all four durations enter the sum; only each robot's own completion time delays that robot (`known_visit_sim/core/scheduler.py:423-429`; `known_visit_sim/core/reallocation.py:430-446`). It is not a sum over physical CPU cores and not the union of nonoverlapping wall intervals. On one physical RP2040, the four measurements are actually serialized for instrumentation, but the simulator maps them back to a common virtual start (`Simulation/Architecture/allocator_replay/causal/session.py:263-271`). HIPC trace 0002 Eager therefore legitimately has 763.026121 processor-seconds in a 276.177379-second mission (`publication/aug14_final_v1/data/primary_trial_level.csv:1451`).

`processor_capacity_fraction` is **not clamped to 1 by code**; there is no `min(1, ...)` in the formula (`known_visit_sim/core/reallocation.py:877-881`). Under the intended four independent, nonoverlapping-per-robot model it behaves like a utilization and normally should not exceed 1, but it is not bounded by definition. A value near 0.69 means 763.026/(4 x 276.177) = 0.6907: the summed allocator work consumes about 69% of the modeled four-robot processor-time capacity. It does not mean allocator timing added 69% to mission time (`publication/aug14_final_v1/data/primary_trial_level.csv:1451`).

## 3. Timing and concurrency semantics

There are two answers to what an allocator call blocks. **Physically**, the Python worker synchronously waits for `provider.measure_group()` (and, for hardware, the serial exchange), so that simulation process does not execute event-loop code during the measurement; the other board-worker processes can continue (`known_visit_sim/core/scheduler.py:721-725`; `Simulation/Architecture/allocator_replay/causal/session.py:943-1004`). **In the scientific discrete-event model**, the returned duration is mapped onto the virtual clock and blocks only its logical robot's processor/control path. The robot is marked compute-busy at the frozen call start and cannot move or start another call until its own virtual completion (`known_visit_sim/core/robot.py:516-567`; `known_visit_sim/core/robot.py:693-741`). It does not block peers, releases, timeouts, movement completions, or message delivery in simulated time. Messages and task admissions whose virtual timestamps fall inside the interval are buffered for that robot and applied after completion (`known_visit_sim/core/robot.py:172-183`; `known_visit_sim/core/robot.py:339-342`; `known_visit_sim/core/robot.py:743-750`). Thus the caller cannot move, but robots already moving can virtually complete moves, other idle robots can act, and arrivals can occur during its call; the scheduler reconstructs that ordering after the physical measurement returns (`known_visit_sim/core/scheduler.py:847-968`).

At an equal simulated timestamp, all eligible robot inputs are frozen before the first host `choose_goal` mutates even a private allocator context (`known_visit_sim/core/scheduler.py:593-645`). Host authoritative decisions are then executed serially in sorted robot-ID order, and physical board measurements are also serial, but outputs are withheld and virtual completions are independent `start + own duration` values (`known_visit_sim/core/scheduler.py:721-817`; `Simulation/Architecture/allocator_replay/causal/session.py:943-1004`). Thus the scientific model is concurrent independent robot processors, represented by per-call virtual delays plus summed processor work—not one global blocking allocator and not a post-hoc single critical-path addition.

The premise of a “four-board AGX campaign” is contradicted. The publication design requires **three** boards/workers (`study/causal/model.py:17-20`; `THREE_BOARD_TEST_REPORT.md:7-9`). Each worker/board runs one simulation at a time and maintains four logical robot contexts; three worker processes are spawned concurrently, so at most three hardware simulations run concurrently (`study/causal/orchestrator.py:663-694`; `study/causal/orchestrator.py:749-768`). An algorithm/load/trace policy block stays on one board, with balanced rotation across three boards (`study/causal/schedule.py:28-34`; `study/causal/schedule.py:67-105`).

The three simulations have independent virtual clocks, but their **physical measurements can be coupled** by shared AGX CPU/memory, USB controllers, serial drivers, thermal/power state, and OS scheduling. Separate core affinities and single-thread environment settings reduce CPU coupling but do not prove it absent (`study/causal/orchestrator.py:465-468`; `study/causal/orchestrator.py:721-730`). Communication/setup contention does not directly enter the injected RP2040 allocator duration, but contention may change `host_program_runtime_s` and may perturb the host `perf_counter_ns` AGX authoritative measurements. The retained evidence does not quantify this coupling: **UNKNOWN**; simultaneous host/USB performance traces would resolve it.

### Real-wall versus simulated/event clocks in the scientific path

- Simulated/event time: absolute task releases, admission/timeout timestamps, message creation/delivery, robot control wakes, turns, waits, route/movement start and completion, allocator virtual start/completion, assignment, and task completion (`known_visit_sim/core/scheduler.py:479-590`; `known_visit_sim/core/scheduler.py:847-968`; `known_visit_sim/comms/bus.py:45-98`).
- Host real monotonic wall time: whole-program runtime via `perf_counter`, AGX `choose_goal` and epoch-reset samples via `perf_counter_ns`, hardware PSETUP/PTIME/result and total-call diagnostic wall durations via `perf_counter_ns`, and serial deadlines/recovery via `monotonic` (`known_visit_sim/core/scheduler.py:432-432`; `known_visit_sim/core/robot.py:221-229`; `known_visit_sim/core/robot.py:580-587`; `Simulation/Architecture/allocator_replay/causal/session.py:591-650`; `Simulation/Architecture/allocator_replay/host/transport.py:1360-1413`). Host `process_time_ns` separately measures preparation CPU, not elapsed simulation time (`Simulation/Architecture/allocator_replay/host/transport.py:1256-1300`).
- Device real monotonic time: MicroPython wrap-safe `ticks_us/ticks_diff` around `choose_goal` and allocation-epoch reset; timer preflight reports units/resolution/monotonicity (`Simulation/Architecture/allocator_replay/builds/micropython_1_24_o0_coalescing_collaborative/replay_worker.py:824-872`; `Simulation/Architecture/allocator_replay/builds/micropython_1_24_o0_coalescing_collaborative/replay_worker.py:1115-1141`).
- Campaign timestamps, retry supervision, and tracker ETA clocks are operational wall time only and never enter a trial's causal event clock (`study/causal/orchestrator.py:490-560`; `study/causal/orchestrator.py:663-735`).

AGX injection uses rounded microseconds from the authoritative host `choose_goal + epoch-reset` samples; the host proxy sets completion to `start + agx_allocator_time_us/1e6` (`known_visit_sim/core/scheduler.py:648-703`; `known_visit_sim/core/timing.py:340-375`). RP2040 injection uses the device-reported sum of the same two allocator components, after parity, at `start + device_duration_us/1e6` (`Simulation/Architecture/allocator_replay/causal/session.py:662-680`; `Simulation/Architecture/allocator_replay/causal/session.py:741-776`). USB/protocol, PSETUP, output serialization, and generic state synchronization are recorded as diagnostics but excluded from causal compute duration (`Simulation/Architecture/allocator_replay/causal/session.py:582-650`; `study/causal/outputs.py:449-469`).

## 4. Zero-compute baseline

Zero-compute does **not** replay causal outputs. The simulator still freezes inputs, calls the authoritative allocator normally, constructs messages/post-state, and records the AGX timing; only after that does `ZeroComputeTimingProvider` return the same authoritative goal/message/state signature with device duration 0 and completion equal to start (`known_visit_sim/core/scheduler.py:634-725`; `known_visit_sim/core/timing.py:382-409`). Output validation rejects any nonzero injected duration in a zero-compute run (`study/causal/outputs.py:470-475`). Decisions are therefore recomputed from that zero-compute run's evolving state, not substituted from its causal pair.

Causal and zero-compute runs can process equal-time work differently. Timed events sort by `(time, priority, insertion order)`; release < timeout < movement/compute completion < control (`known_visit_sim/core/scheduler.py:91-98`; `known_visit_sim/core/scheduler.py:493-525`). All events within 1e-12 are batched, sorted, then due messages are pumped in `(delivery time, bus insertion order)` before sorted robot-ID call/control processing (`known_visit_sim/core/scheduler.py:866-968`; `known_visit_sim/comms/bus.py:22-27`; `known_visit_sim/comms/bus.py:84-98`). Exact-zero completions create same-timestamp microsteps, with a guard preventing an unbounded immediate recursion until new timed information or a message arrives (`known_visit_sim/core/scheduler.py:859-876`; `known_visit_sim/core/scheduler.py:907-968`). A positive AGX/RP2040 duration instead allows releases, peer moves/computes, and messages to occur before that robot commits.

That difference explains why even small AGX timing can alter `max_robot_steps`. A delayed commit can see buffered messages/admissions after its chosen result, can temporarily expose a stale goal, and can change which assignment/consensus/collision event occurs first (`known_visit_sim/core/robot.py:693-750`). A changed goal or peer-intent view changes A* blocking, bundle repair, and the subsequent route; movement duration is paired for the same action/edge, but the action sequence itself need not remain the same (`known_visit_sim/core/planner.py:48-83`; `known_visit_sim/core/robot.py:773-827`; `known_visit_sim/core/scheduler.py:42-81`). Thus near-zero mean AGX mission-time effect does not imply identical paths or that AGX timing is literally outside the event graph.

## 5. Policy semantics

All policies begin with one mandatory time-zero `initial_allocation` epoch containing the eight initially visible tasks and one expected first call per robot (`known_visit_sim/core/reallocation.py:473-491`). Every positive-time release enters the one global pending queue in release-time/task-index order (`known_visit_sim/core/reallocation.py:521-532`). There is no separate batch counter: current queue length is the count, and every admission drains the entire queue (`known_visit_sim/core/reallocation.py:493-507`; `known_visit_sim/core/reallocation.py:662-686`).

| Policy | Arrival trigger and below-threshold tail | Timeout/reset behavior |
|---|---|---|
| Eager B=1 | Every nonempty release batch is immediately and globally admitted with `task_arrival_eager`; pending depth normally samples as one, except multiple exact-time releases are collected together (`known_visit_sim/core/reallocation.py:521-536`). | No W is legal for Eager (`known_visit_sim/core/reallocation.py:48-68`). |
| Count B=2 | Hold until `pending_count >= 2`, then admit the whole queue with `batch_threshold`. If the last exogenous release leaves fewer than 2, admit it immediately with `final_release_flush` (`known_visit_sim/core/reallocation.py:537-542`). | No timeout. Queue depth resets to 0 on admission; a new count begins with the next release (`known_visit_sim/core/reallocation.py:662-686`). |
| Count B=4 | Same with threshold 4 and final partial-tail flush (`known_visit_sim/core/reallocation.py:537-542`). | No timeout; queue clear is the reset. |
| Count B=8 | Same with threshold 8 and final partial-tail flush (`known_visit_sim/core/reallocation.py:537-542`). | No timeout; queue clear is the reset. |
| Bounded B=4/W=5 | Admit at whichever occurs first: depth >=4, oldest pending age reaches 5 simulated seconds, final partial-tail release, or a mandatory piggyback (`known_visit_sim/core/reallocation.py:509-549`; `known_visit_sim/core/reallocation.py:551-567`). | Deadline is recomputed as `min(pending release)+5`. Clearing the queue cancels its logical clock; the next pending task starts a new oldest-release clock (`known_visit_sim/core/reallocation.py:509-519`; `known_visit_sim/core/reallocation.py:662-686`). |

Mandatory reallocations do not wait for B or W. A task completion is opened at physical service, an invalid goal is opened at the failure site, and robot-idle is detected at a safe control/call boundary (`known_visit_sim/core/robot.py:1138-1167`; `known_visit_sim/core/robot.py:1216-1257`; `known_visit_sim/core/scheduler.py:593-611`). If pending tasks exist, all are admitted into that mandatory epoch, the epoch becomes global, and `piggybacked_pending=True`; consensus/internal polling is explicitly forbidden from bypassing batching (`known_visit_sim/core/reallocation.py:551-617`).

An epoch is one logical trigger/admission record. A call is one robot invocation. A global admission/initial epoch initially expects one first call from each of four robots; a local invalid-goal epoch may initially expect only the affected robot, and a completion epoch initially expects the completing robot while associating subsequent peer work with the same global epoch (`known_visit_sim/core/reallocation.py:551-586`; `known_visit_sim/core/reallocation.py:619-652`). Later consensus/internal, outbid, goal-loss, collision, or idle decisions can generate further calls that remain associated with the robot's most recent active epoch (`known_visit_sim/core/reallocation.py:588-652`; `known_visit_sim/core/robot.py:484-514`). Epoch “closure” records only that each expected robot made its first call; it does not terminate association or certify consensus (`known_visit_sim/core/reallocation.py:421-426`). There is no fixed calls-per-epoch maximum short of the trial event horizons (`known_visit_sim/core/scheduler.py:819-844`). This is why calls per epoch can be far above four, and a larger admitted task set can create more asynchronous calls inside one epoch.

### Why low-load batching increases calls despite fewer epochs

This is confirmed arithmetically, but only partly mechanistically. In the zero-compute low-load conditions, mean Eager -> Count-B=4 calls/epochs were: ACBBA 1,887.72/111.96 -> 2,170.42/72.22; CBAA 1,829.54/115.88 -> 2,105.44/71.64; HIPC 2,118.32/92.74 -> 2,361.26/66.96; PI 1,955.78/99.24 -> 2,242.56/87.00 (`publication/aug14_final_v1/data/primary_condition_summary.csv:69-71`; `publication/aug14_final_v1/data/primary_condition_summary.csv:84-86`; `publication/aug14_final_v1/data/primary_condition_summary.csv:99-101`; `publication/aug14_final_v1/data/primary_condition_summary.csv:114-116`). The implied ratio-of-means calls/epoch rises from 16.86 to 30.05, 15.79 to 29.39, 22.84 to 35.26, and 19.71 to 25.78 respectively.

The code-consistent mechanism is: sparse arrivals often leave no active goal, so a genuine `robot_idle` call can admit the pending tail early; admission resets every allocator and starts four contexts, while the larger simultaneously admitted active set creates more message/consensus/internal calls before the next epoch (`known_visit_sim/core/scheduler.py:593-630`; `known_visit_sim/core/reallocation.py:598-617`; `known_visit_sim/algorithms/base.py:83-97`). This supports the user's hypothesis with one refinement: “no current goal” is not always classified `robot_idle`; it is `robot_idle` only when the robot has no active tasks, otherwise it is typically `initial_allocation` or `consensus/internal` (`known_visit_sim/core/robot.py:484-514`). Exactly which inner message or goal-loss transitions account for the added calls is **UNKNOWN** without the omitted per-call raw artifacts.

W=5 is a hard upper bound on **scheduler pending-queue age at admission** under normal event-loop completion: a timeout is scheduled exactly at oldest release + 5 and cannot fire early (`known_visit_sim/core/reallocation.py:509-549`; `study/causal/outputs.py:705-709`). It is not a bound on release-to-assignment latency, release-to-completion latency, or the time until every robot can use the admission. Admissions are timestamped at W even for compute-busy robots, whose local application is buffered until compute completion (`known_visit_sim/core/robot.py:172-183`). A run terminated by an algorithmic/event horizon before the deadline is an exception to a mission-wide guarantee, and floating comparisons use 1e-12 in the scheduler/1e-8 in validation (`known_visit_sim/core/reallocation.py:525-549`; `study/causal/outputs.py:705-709`).

## 6. Algorithm-specific call structure

No algorithm has a simulator-level blocking “solve to convergence.” Every call is one local robot invocation; consensus occurs asynchronously through delayed messages and later calls (`known_visit_sim/core/robot.py:569-648`; `known_visit_sim/comms/bus.py:45-98`).

| Algorithm | One call and practical scaling |
|---|---|
| CBAA | One `pick_goal`: keep the current won task if valid, otherwise scan all grid cells to form active candidates and make one bid/claim choice. It owns one task, merges received winner/bid deltas asynchronously, and uses lower robot ID for equal bids (`known_visit_sim/algorithms/CBAA.py:23-88`; `known_visit_sim/algorithms/CBAA.py:90-120`; `known_visit_sim/algorithms/CBAA.py:235-306`). Practical call cost is O(grid area + active candidates); no inner consensus-round loop is counted. Admission clears winner/bid/current-task/delta caches (`known_visit_sim/algorithms/CBAA.py:355-362`). |
| ACBBA | Repair a bundle after consensus, then greedily fill a size-3 bundle. Each fill scans active candidates and tries every insertion position, with route-cost recomputation; losing a bundle element releases that element and its suffix (`known_visit_sim/algorithms/ACBBA.py:14-69`; `known_visit_sim/algorithms/ACBBA.py:71-168`; `known_visit_sim/algorithms/ACBBA.py:217-266`). Practical cost grows roughly with up to 3 fill slots x active candidates x insertion/route length. Admission resets all winner/bid/bundle/path state (`known_visit_sim/algorithms/ACBBA.py:692-710`). |
| HIPC | Build a local team-level task-allocation approximation on each call, then keep this robot's slice of a size-3 plan. Candidate formation scans/sorts the grid; local team formation considers visible peers; the team allocator performs up to `team_size*3` assignments and, for each, loops over eligible team robots and candidates (`known_visit_sim/algorithms/HIPC.py:48-121`; `known_visit_sim/algorithms/HIPC.py:123-177`; `known_visit_sim/algorithms/HIPC.py:179-245`). With four peers this is up to 12 nested selection rounds, making it the heaviest practical call as active tasks grow. Admission resets winner/bid/path/bundle and team-plan caches (`known_visit_sim/algorithms/HIPC.py:699-718`). |
| PI | Repair/refill a size-3 path. Each refill scans active candidates; each candidate tests each insertion position and recomputes route cost, choosing lower marginal significance/cost (`known_visit_sim/algorithms/PI.py:34-80`; `known_visit_sim/algorithms/PI.py:82-151`; `known_visit_sim/algorithms/PI.py:424-445`). Practical cost is roughly up to 3 fills x active candidates x insertion/route length. Admission resets owner/significance/time/path/bundle state (`known_visit_sim/algorithms/PI.py:744-757`). |

HIPC's hardware/AGX work ratio is much larger because its deeply nested team planning executes in MicroPython on the RP2040. Across the 26 hardware HIPC trials the mean/median RP2040:AGX work ratios are 50.095x/47.602x, versus ACBBA 26.715x/26.449x, CBAA 26.839x/26.600x, and PI 21.398x/22.815x (`publication/aug14_final_v1/data/hardware_summary.csv:3-6`). At high load, many active tasks feed the team-agent x candidate x assignment nesting (`known_visit_sim/algorithms/HIPC.py:179-245`), so repeated calls can create extreme summed work. This is a strong code/data explanation, but the exact language/runtime/cache contribution is **UNKNOWN** without an RP2040 instruction or line profiler.

In the balanced four-trace high-load hardware core, Count-B=4 minus Eager means are: ACBBA mission +22.262 s/work -12.137 s/team steps +25.5; CBAA mission -0.611 s/work -3.828 s/team steps +9.25; HIPC mission -88.252 s/work -397.816 s/team steps +20.75; PI mission -21.915 s/work -54.411 s/team steps +1.0. ## 7. Hardware parity

Parity is checked **per allocator call**, before that call's duration can enter the mission. The compared input is the frozen call setup: algorithm, robot/context, virtual start, call class, active-task/candidate view, current position, pre-state, and the ordered admissions/messages/device events presented to that context (`known_visit_sim/core/scheduler.py:674-720`; `known_visit_sim/core/robot.py:516-567`; `Simulation/Architecture/allocator_replay/causal/session.py:943-972`). The direct output signature comparison requires exact equality of goal, active-candidate count, outbound-message SHA-256, post-state SHA-256, and call class; ordered event/message serialization preserves tie order, and there is no numerical tolerance (`Simulation/Architecture/allocator_replay/causal/session.py:466-490`). If only representation hashes differ, the bridge projects both message effects and algorithm state to a common logical schema and still requires exact structural equality; it records that weaker representation-level route explicitly (`Simulation/Architecture/allocator_replay/causal/session.py:693-740`; `Simulation/Architecture/allocator_replay/causal/parity.py:500-540`). Any remaining mismatch rejects the duration and invalidates the entire same-time group/mission attempt (`Simulation/Architecture/allocator_replay/causal/session.py:741-775`; `Simulation/Architecture/allocator_replay/causal/session.py:943-1004`). Epoch/trial parity follows only because every included call passed.

All allocator calls in all 104 hardware trials were required to use the bound physical RP2040: the production provider opens a real serial device and validates expected UID/build/module/firmware identities; only an explicit development override can use a simulated provider (`study/causal/worker.py:51-100`). Output validation checks every call's robot/context, board UID, parity, native-hardware attestation, and hardware validation mode (`study/causal/outputs.py:364-385`; `study/causal/outputs.py:470-489`). There is no AGX fallback path inside a hardware trial. AGX still recomputes the authoritative decision for parity and records AGX work, but its duration is not the hardware trial's injected duration (`known_visit_sim/core/scheduler.py:634-725`).

## 8. Arrival-load and mission semantics

| Load | Rate | Mean interarrival | Process |
|---|---:|---:|---|
| low | 0.075 tasks/s | 13.333 s | accumulated Exp(rate=0.075) |
| medium | 0.3 tasks/s | 3.333 s | accumulated Exp(rate=0.3) |
| high | 1.2 tasks/s | 0.833 s | accumulated Exp(rate=1.2) |

The numerical rates and units are frozen in all campaign configs (`configs/agx_deadline_primary_1396_v1.json:3-17`; `configs/agx_n50_extension_causal_1500_v1.json:3-17`). Each trace contains 50 tasks, eight at time zero and 42 online. A single Exp(1) draw sequence is shared across loads and divided by rate; spatial, arrival, and runtime random streams are independently SHA-derived (`study/manifests.py:1-6`; `study/manifests.py:42-46`; `study/manifests.py:155-198`). Algorithms and policies use the exact same scenario/release manifest within each trace/load, enforced by manifest validation and the 4 x 3 x 5 x 50 matrix key (`study/manifests.py:280-309`; `scripts/agx_build_final_publication.py:948-953`).

There is no fixed simulated time horizon. Releases continue according to the 42-entry absolute schedule, and a normal mission ends when all 50 tasks complete (`known_visit_sim/core/world.py:280-281`; `known_visit_sim/core/scheduler.py:939-942`). Noncompletion instead uses event-count horizons: 251,000 total causal events and 5,500 events without the limited progress signature changing (`known_visit_sim/core/scheduler.py:819-844`; `study/causal/outputs.py:860-869`).

The mission is a 19 x 19 grid with four robots starting at `(0,0)`, `(0,6)`, `(0,12)`, `(0,18)`, all heading east (`study/generated/manifests/collaborative_visit_g19_t50_n50_extension_v3/scenarios/trace_0000.json:2-35`). The 50 task cells are sampled uniformly without replacement from all non-start cells (`study/manifests.py:117-151`). Motion is one adjacent four-neighbor cell per committed step, using A* and explicit turn/intent/move actions (`known_visit_sim/core/planner.py:26-83`; `known_visit_sim/core/robot.py:1048-1072`; `known_visit_sim/core/robot.py:1124-1144`). Robots block cells occupied or intended by peers, replan, and eventually quarantine repeatedly blocked goals; this is a protected coordination model rather than rigid-body dynamics (`known_visit_sim/core/robot.py:1192-1242`). Completion occurs on first post-admission physical arrival or stationary service of every task (`known_visit_sim/core/world.py:185-219`; `known_visit_sim/core/robot.py:1277-1330`).

First-assignment latency is not necessarily on the mission critical path. While a newly released task waits, robots can finish already assigned tasks or move toward locations that later make service cheap; a robot can also physically cross the cell and assign/service it at the same timestamp (`known_visit_sim/core/world.py:201-218`). Delayed assignment can be compensated by parallel robot work, different bundling, shorter later routes, or the fact that low-load mission time is bounded by the last release. It remains a useful responsiveness metric, but mission time, completion/liveness, processor work, calls/epochs, and movement steps answer different questions.

### Multiple testing and statistical units

Benjamini-Hochberg is implemented once and applied only to paired-*t* mission p-values (`scripts/agx_build_final_publication.py:283-314`). The exact families are:

- `paired_condition_summary.csv`: one family of 60 algorithm x load x policy causal-minus-zero mission tests (`scripts/agx_build_final_publication.py:364-399`; `scripts/agx_build_final_publication.py:959-959`).
- `paired_factor_summary.csv`: a separate family within each call to `_group_summary`: overall (1), algorithm (4), load (3), policy (5), algorithm x load (12), algorithm x policy (20), and load x policy (15). They are **not** one combined 60-test factor family (`scripts/agx_build_final_publication.py:517-534`).
- `policy_vs_eager_summary.csv`: separate families for the policy level (2 datasets x 4 non-Eager policies = 8) and condition level (2 x 4 algorithms x 3 loads x 4 policies = 96) (`scripts/agx_build_final_publication.py:473-514`).

Wilcoxon p-values and nonmission metrics receive no BH q-value (`scripts/agx_build_final_publication.py:283-314`).

Noncompletions remain in planned/completion denominators but are omitted from mission-time and other pair differences requiring both missions to complete (`scripts/agx_build_final_publication.py:329-360`; `scripts/agx_build_final_publication.py:402-427`; `publication/aug14_final_v1/RESULTS.md:50-52`). Task rows are used only for descriptive aggregation; the report explicitly says they are not independent experimental replicates (`scripts/agx_build_final_publication.py:684-732`; `publication/aug14_final_v1/RESULTS.md:72-76`).

All 50 trace IDs are reused across all 60 conditions in each timing dataset; coverage is enforced as 4 x 3 x 5 x 50 (`scripts/agx_build_final_publication.py:948-953`). Condition-level paired differences use trace as the correct paired unit. However, factor-level confidence intervals simply pool trial-level differences and apply an ordinary Student-*t* interval, without trace blocking, clustered standard errors, repeated-measures modeling, or algorithm/load/policy random effects (`scripts/agx_build_final_publication.py:255-265`; `scripts/agx_build_final_publication.py:364-399`; `scripts/agx_build_final_publication.py:517-534`). They therefore treat repeated appearances of a trace across factor cells as independent for variance estimation. Point means remain descriptive; factor-level CIs/p-values do not fully respect the crossed repeated-trace design.
